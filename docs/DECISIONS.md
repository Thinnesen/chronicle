# Decisions

One entry for each design change. Newest first.

- 2026-10-20: A semaphore can read its limit from a key of a ConfigMap (`configMapKeyRef`), as in Argo. The controller reads the ConfigMap past its cache each time a run or a node asks for the lock. So a new limit counts at the next try, and holders above the new limit keep the lock. The ConfigMap needs the label `chronicle.thinnesen.com/parameters: "true"`, as for parameters. A missing ConfigMap, label, key or number holds the run or the node back, with the reason in its message. Kubernetes does the same for a Pod with a missing ConfigMap. An Error in the middle of a run would leave Pods and locks of other nodes behind. Reason for the feature: a platform team can change the limit without a change of the workflows. The converter names the lock after the ConfigMap name and key, so runs that share the key share the lock. This replaces part of the entry of 2026-10-19 about locks.

- 2026-10-20: The init container downloads the input artifacts into an emptyDir. The main container mounts each input with `subPath` at its path, as in Argo. Before, the main container downloaded the inputs. So a step without root could not get an input at a path such as `/src`. Outputs still need a writable path, because the step writes them itself. A failed download fails the init container. Its termination message becomes the node message.

- 2026-10-20: DAG tasks and steps can have an exit hook (`onExit` with a template and arguments). The rules are those of Argo v4. The tasks after a task wait for its hook. A hook that ends Error fails the DAG or the steps. A hook that ends Failed does not. A fan-out runs its hook once after all items. Argo runs it once for each item; one hook keeps the node tree simple. chronicle has no expressions, so it has no hooks with expressions.

- 2026-10-20: A container, script, resource or http template can have `memoize`, as in Argo. The results are in the archive database. Argo keeps them in ConfigMaps. That needs write access to ConfigMaps, so the controller could change any ConfigMap. The engine stays pure. It asks for the cache keys with an action. The controller then runs the same engine step again with the answers. So no state stays between two steps. A hit ends the node without a Pod.

- 2026-10-20: A container, script, resource, http or task template can have a lock (`synchronization`), as in Argo. Each node holds the lock while it runs. The engine stays pure. It asks for the lock with an action. It starts the node when the controller reports the lock as held. It gives the lock back when the node ends. The template locks use the same Leases as the run locks, with the node ID in the holder. Before, the converter dropped Argo template locks. So a converted pipeline could run two migrations at the same time.

- 2026-10-20: Workflow parameters and input parameters can read a ConfigMap (`valueFrom.configMapKeyRef`), as in Argo. The controller reads the ConfigMap once when the run starts. It keeps the values in `status.storedSpec`, as it does for resolved template references. So a change of the ConfigMap during a run does not change later steps. The ConfigMap needs the label `chronicle.thinnesen.com/parameters: "true"`. Reason: the controller can read all ConfigMaps. A user who may create Workflows must not read other ConfigMaps through a run. Argo has the same opt-in label.

- 2026-10-20: The controller fails a run when its Workflow would be larger than 1 MiB. It does this before it applies the actions of that engine step. Before, the status update failed at each reconcile. The run looked stuck, and its Pods went on. Argo moves large node lists into its database ("offloading"). Then each run depends on the database, and the status in the cluster is not complete. A clear failure with a hint to split the work is simpler. Offloading stays an option if real runs need it.

- 2026-10-20: `withSequence` is a field of a DAG task or a step, as in Argo. The engine expands it when the run starts the task. Before, the converter expanded it to `withItems`. That failed when the count came from a parameter. The format must have exactly one integer verb. So a format cannot read other arguments.

- 2026-10-20: An `http` template sends its request from a Pod in the namespace of the run. The Pod runs `chronicle-exec http` and has no API token. Argo sends the request from an agent Pod with its own service account and RBAC for task results. A plain Pod keeps one model for all steps: network policies, quotas and logs apply as for a container. A header value from a Secret is a `secretKeyRef` environment variable. So the controller never reads Secrets. chronicle has no expressions, so success is a status from 200 to 299.

- 2026-10-20: An input artifact can come from `raw` text or from an `http` URL, as in Argo. This is also possible in `spec.arguments.artifacts`. The step downloads the URL from its own Pod. So the controller and the server make no requests to user URLs. The executor saves the file as it is. Argo unpacks a file that it detects as a tarball. A file that changes its form because of its content is a surprise, and a step can unpack it. Each other Argo source (s3, gcs, git and others) needs its own credentials. chronicle does not support them. Use the repository of the namespace.

- 2026-10-20: The node outputs in the status have `exitCode`, the exit code of the main container, as in Argo. The controller reads it from the Pod status. So the exit code is there also when the executor wrote no message. New placeholders: `{{tasks.x.exitCode}}`, `{{steps.x.exitCode}}`, and the node fields `id`, `startedAt` and `finishedAt`. A fan-out has no `exitCode`, because its items can have different codes.

- 2026-10-20: Global outputs as in Argo: `globalName` on output parameters and artifacts, `status.outputs`, and `{{workflow.outputs.*}}`. The engine computes the outputs from the finished nodes at each engine step. So a retry or a re-run gives the same result as its nodes. Reason: exit handlers and runs that report one result need global outputs. The Argo converter dropped them.

- 2026-10-20: A DAG task or a step can have `continueOn` (`failed`, `error`), as in Argo. A failure that continues counts as success for the `depends` of later tasks. It does not fail the DAG or the steps. The node stays Failed. Reason: a steps template has no `depends`. So users who came from Argo could not go on after a failed step.

- 2026-10-20: An approval has an optional `user`. The API sets it to the caller. The validating webhook refuses a new or changed approval when its `user` is not the user of the admission request. Kubernetes does the same for the username of a CertificateSigningRequest. An approval without a user stays allowed, so `kubectl patch` still works. Reason: no durable record told who approved. The audit log is not durable, and Kubernetes events stay for one hour. Argo has no such record either.

- 2026-10-20: The CSP allows injected styles with a nonce for each page (`style-src 'self' 'nonce-...'`). The server puts a new random nonce into index.html and into the header of each page. The UI gives the nonce to `get-nonce`, and the scroll lock of the dialogs reads it there. Reason: each Radix dialog injects a `<style>` for its scroll lock. The CSP blocked it. So the lock did not work, and each dialog logged a violation. `'unsafe-inline'` would allow CSS injection. A hash does not work, because the style depends on the width of the scrollbar.

- 2026-10-19: The `synchronization` locks are Kubernetes Leases (`chronicle-lock-<name>`). An annotation holds the holders. The controller reads the Lease past its cache. It writes the Lease with the resource version of the read. So two reconciles can never both take the last slot. A finished run gives the lock back. When another run asks for the lock, the controller drops the holders that were deleted or have finished. The limit of a semaphore is in the spec, not in a ConfigMap as in Argo. Reason: deployment pipelines need "one at a time". Leases need no extra store and no finalizer. Cost: the controller needs `get`, `create` and `update` on Leases in all namespaces. RBAC cannot limit a rule to a name prefix. So a compromised controller could change other Leases, for example those of leader elections. It can already create Pods in all namespaces, which is a larger power.

- 2026-10-19: `parallelism` (of the workflow, and of a `dag` or `steps` template) counts only Pods. It does not count task nodes or suspend nodes. The message of a Pod node tells that it waits. An admitted Pod holds its slot also before the cache shows it. So a run never goes over a limit. Reason: a fan-out of many items must not start all its Pods at the same time. This was the Argo feature that users missed most. Task workers limit their own work with their concurrency.

- 2026-10-19: With an archive database, the login sessions of the UI are in that database. The table is `sessions`, with a hash of the session ID as the key. Reason: the memory store logged out all users at each restart, and it allowed only one server replica. A signed cookie without server state could not end a session at logout. Without an archive, the memory store stays. Then the chart refuses more than one server replica with a login.

- 2026-10-19: With an archive, the history limits of a CronWorkflow delete a run only after the archive has it. The TTL does the same. A user who deletes a run by hand still deletes it at once. There is no finalizer, because a finalizer would block deletes while the archive is down. A list goes to the next page with a cursor, not with an offset. The cursor is the creation time and the name of the last run. So a deep page in a large archive costs the same as the first page. These are findings of the code review (#36).

- 2026-10-19: The containers of the chronicle image in workflow Pods have a read-only root file system. These are the init container of the executor and the resource steps. The container of a user step has a writable root file system. Reason: many user images write to their root file system, for example to `/tmp` or to a cache. The step still runs without root and without capabilities. There is no `podSpecPatch`, because a patch could undo the security settings of the Pod. Section 3.2 promised a limited one. The security review (#36) found this.

- 2026-10-19: The web UI is an ops console. It has a sidebar, a Cmd+K search, a node drawer and the tabs Graph, Timeline and Spec. It is not the signal-box panel of section 8.1. Status icons replace the signal lamps. The graph does not show the root node. Reason: the owner found the first UI "vibecoded" and chose the ops console. The design combines ideas of Argo Workflows, Argo CD, Temporal and Dagster (docs/RESEARCH.md).

- 2026-10-19: A dependency version must be at least seven days old. A release that fixes a known vulnerability is the exception: then the fix wins. The first case was rustls 0.23.46. Dependabot enforces the seven days with a cool-down. For pnpm, `minimumReleaseAge` is a hard minimum of one day for each install, also by hand. Trivy scans the image and all lockfiles in CI and each week. The Makefile pins Trivy with a SHA-256. It does not use the trivy-action, because attackers once took over its tags.

- 2026-10-19: Task workers: the queue is a table in the archive database. A timeout fails the attempt, with no silent second delivery. Only `retryStrategy` makes retries. Reason: Pods and tasks have one retry mechanism. A result that comes after a timeout can never change a finished node. Temporal also fails an activity attempt on a heartbeat timeout and retries by its policy.

- 2026-10-19: The Python and Rust SDKs are hand-written builders that make plain objects. They have no generated types and no runtime dependencies. The Python client uses only the standard library. The server validates a workflow when it gets it. A shared test fixture keeps the output of the three SDKs equal. Reason: generated CRD types are large and need a generator and dependencies. They give little to a builder API. Section 6 said that the SDKs generate their workflow types from the CRD schema.

- 2026-10-19: Each namespace has one S3-compatible artifact repository, from a ConfigMap and a Secret with a fixed name. The value of an artifact is its key. The archived log is the node field `logKey`, not an artifact. Reason: a team owns its storage and its credentials. The fixed name lets the server read only these Secrets. Keys use the same flow in the engine as parameters. Argo has more storage drivers and a default repository in the controller ConfigMap. chronicle supports only S3 for now.
- 2026-10-19: The e2e tests use SeaweedFS as the S3 store, not MinIO. Reason: MinIO no longer publishes container images. Issue #25 named MinIO.

- 2026-10-18: A retry is the spec field `restart` with a generation. A retried Pod gets the generation in its name. Reason: kubectl, GitOps, the CLI and the UI use the same mechanism. The status stays owned by the controller. A new Pod can never look like a terminating Pod of the same node. Argo resets the nodes through its own API and uses the Pod names again.

- 2026-10-18: The API carries Workflows as JSON objects (`google.protobuf.Struct`), not as protobuf copies of the CRD types. Reason: a workflow has one definition, the Go types and the CRD. Section 2 said that the SDKs come from the protobuf API. Now only the API clients come from it.
- 2026-10-18: The server impersonates the caller for each Kubernetes call, reads included. It has no mode without authentication. Reason: the threat model allows no server-side privilege for user actions. The cost is one API client for each request.

- 2026-10-18: A resource template runs in a Pod with the service account of the workflow. It does not run in the controller, and it does not use impersonation. Reason: so the controller needs no `impersonate` permission. A step can do only what its service account can do. The engine parses a manifest before it puts the values in. So a parameter cannot inject YAML.

- 2026-10-18: Suspend, stop, terminate and approvals are fields of the Workflow spec (`suspend`, `shutdown`, `approvals`). Reason: kubectl, GitOps, the CLI and the UI use one mechanism with the same RBAC (`update` on Workflows). Argo uses spec fields for suspend and shutdown. For resume and approvals, it changes the nodes through its own API.

- 2026-10-18: A workflow Pod reports its outputs in the termination message of its main container. `chronicle-exec` writes the message. Reason: Argo needs a `WorkflowTaskResult` resource and API access for each Pod. Without API access, a compromised step cannot change a Kubernetes object. The cost is a limit of 4 KiB. Artifacts carry larger data. Kubernetes image volumes could replace the init container later, when all supported runtimes have them.

- 2026-10-18: The engine parses a `when` condition before it puts the values in. Each value is one literal operand. Reason: Argo puts the values into the text of the expression. So a parameter value such as `x || true` can change the condition (injection). The Argo converter keeps simple conditions as they are.

- 2026-10-18: The outcome of a DAG follows Argo v4: the leaf tasks and their branches decide. There is one change. A failure that a task tests for with its exact result (`a.Failed`, `a.Errored`) counts as handled. It does not fail the DAG, and `failFast` does not stop the DAG because of it. Reason: in Argo, an omitted leaf such as `depends: "!a.Failed && b"` fails the DAG after a handled failure. That surprises users.

- 2026-10-18: The template container is a small chronicle type without a security context. A script source cannot have placeholders. Reason: a user who can create a Workflow must not get a privileged Pod. Parameters must never become shell code (threat model, section 6.2). Argo YAML with placeholders in a script source must move them to environment variables. The converter does this for shell scripts.

- 2026-10-18: Microsoft Entra ID (Microsoft 365) is a first-class identity provider. It supports group overage through Microsoft Graph and access for each team through the Helm value `teams`. Reason: the owner wants an easy M365 login, and platform admins want to see each team's work.
- 2026-10-18: The engine is a pure package, with no I/O and no clock. The controller applies its result. Reason: the workflow logic is deterministic, and table tests and fuzz tests can check it.
- 2026-10-18: Permissions come from Kubernetes SubjectAccessReview and impersonation. Reason: the UI, the CLI, `kubectl` and GitOps share one RBAC model. Argo Workflows needs a separate SSO RBAC mapping, which users find hard.
- 2026-10-18: The API uses Connect-RPC: gRPC and HTTP/JSON from one protobuf definition. Reason: the SDKs for Go, Python and Rust come from one source, and the UI can use plain HTTP/JSON.
- 2026-10-18: chronicle has its own API group (`chronicle.thinnesen.com`), not the Argo group, and a converter for Argo YAML. Reason: chronicle and Argo Workflows can run in the same cluster during a migration.
- 2026-10-18: Durable task workers (activities) come first, durable workflow code later. Reason: deterministic replay of user code is a large, separate problem. Retries of steps and re-runs cover most needs.
